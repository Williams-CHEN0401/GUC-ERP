## 2 啟用前須備妥

1. 確認本次最終程式版本、PR 審閱與發布時段。重新 fetch 並比較當時 main、正式來源與目前基準 `ae701853e5af0d63bd2b0fe7607d3c40b56e7b5b`，保留多人指派及施工監控既有功能。任何來源或 schema 漂移先重做相容驗證。
2. 公司確認實際受評人、指定主管、其他管理員核定人、職務配比、績效角色權限、90 天試評起算、生效日期與人事資料保存政策。無其他合格核定人時，不繞過自我核定限制。
3. 公司確認回覆工作日數、每週工作日與假日表；未確認時不設定逾期期限，保留待回覆狀態。
4. 使用代表性手機實機完成本人查看、回覆及主管審核；由指定試用人員完成合成資料流程。WebKit 自動測試不作為實機簽核。
5. 保存現行 ERP 映像 digest、Gateway 檔案、compose 與環境設定；完成可還原資料庫備份並確認還原方式與空間。備份不得納入 Git 或公開附件。

## 3 發布程序

1. 保持 ERP 與 Gateway 的 `GUC_PERFORMANCE_ENABLED=false`。先驗證正式 URL、內網 URL、登入及既有日誌／指派／取貨讀取正常。
2. 唯讀記錄 PostgreSQL 版本、現行 role_permissions CHECK、RLS／ACL、已部署施工監控與多人指派 RPC 定義。檢查是否已存在任一 performance 表或函式；若存在先判讀狀態，不能覆蓋既有考核資料。
3. 在已備份的正式資料庫依序套用精確三份 SQL，記錄開始／結束、SHA 與交易結果。第一份會短暫鎖定 role_permissions；遇 lock_timeout 停止並改時段，不延長鎖或刪除資料硬套。
4. 通知 PostgREST 重載 schema，確認 14 張績效表、索引、不可變更 trigger 與 RPC；檢查 RLS 開啟、anon／authenticated 無直接權限、service_role 能從既有路徑操作。此步驟不批次建立真實評核。
5. 僅更新受影響的 ERP 與 Gateway 服務，保持旗標關閉。確認靜態權重 JSON 正常，而 package、環境設定、憑證與其他私有檔案仍拒絕存取。
6. 檢查正式及內網的登入、權限、日誌、多人指派、取貨與施工監控既有功能。確認 performance 入口隱藏、GET／POST 拒絕。出現異常立即依第 5 節回復。
7. 設定已核定的績效角色權限，雙端同步啟用旗標，只安排已指定試用人員及月份。先建立 JSON 初始模板的新版本，再建立試評月份、指定關係與配比。來源 JSON 的 proposal_not_deployed 與空白生效日不代表公司已核定政策。
8. 以核准試評資料完成評級→回覆→核定→發布→本人查詢／匯出，檢查分數、版本、來源授權與稽核；不得擅自代替真實員工回覆或核定。
9. 記錄發布 commit、映像標籤與 digest、SQL SHA、操作時間、驗證證據、試用名單及回復版本。需要同步 GitHub／Docker Hub 時，依當次正式發布授權與既有發布流程執行。

## 4 試評與觀察

試評以核定起算日計 90 天；定期由負責人查閱權限拒絕、409 衝突、失敗請求、等待回覆及資料不足案件。重點確認 N/A 判斷、具體說明與佐證品質，工單筆數或請假天數不自動換成分數。試評結束由公司確認正式生效；本期沒有自動生效或自動核定排程。

新增資料未授予非管理員既有角色預設權限；主管指定關係也不自動開放私人案場。調整權限必須沿用現有管理介面並留下稽核。

## 5 回復方式

- 功能或權限異常：先在 ERP／Gateway 同時關閉績效旗標，重建這兩個受影響服務並確認入口及 API 均關閉；驗證既有 ERP 流程。
- 程式相容問題：回復已保存 ERP 映像與 Gateway 版本。新增表與 RPC 原則上保留，以維持考核及稽核歷史；不可刪表重建作為一般回復措施。
- Migration 失敗：失敗檔案的交易回滾；保留先前已成功檔案及執行紀錄，旗標維持關閉。依實際狀態修正並在隔離環境重驗，不能盲目重播全部三份。
- 只有已確認資料毀損且經核定的維護處置，才使用資料庫備份還原；須評估備份時間之後其他 ERP 寫入，不可把整庫回復當成單一模組的一般回復。

完成上述啟用條件並獲得正式發布指示後，才進入正式部署；本次交付僅完成隔離開發、測試與此發布計畫。
