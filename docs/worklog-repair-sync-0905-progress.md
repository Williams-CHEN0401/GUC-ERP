# 工作日誌第二次修正：實作與驗證紀錄

分支：`codex/worklog-repair-sync-0905`。
狀態：程式修改與本機驗證完成，尚未推送、套用遠端 SQL 或發布網站。

## 已確認方案

使用者於本次回覆「是」，同意儲存工作日誌時一併建立維修品，只帶入客戶、品項與備註；收件日期、數量、狀態、故障內容等未知值留白，在既有維修品介面後續補齊。日誌、明細、設備連結及維修品任一步失敗，整筆交易回滾。

## 完成內容

- 新增工作日誌先等待施工人員清單載入，再直接開啟表單；移除表單外的維修確認視窗。
- 表單內詢問「是否要登錄維修品」；選「是」顯示一筆可編輯維修明細，既有多筆事件功能保留。
- 設備改為選填。未選設備不建立設備履歷連結；選設備保留原客戶／承攬內容／設備啟用狀態驗證。
- 新增設備種類、設備品項。先選種類再選對應品項，切換或清除種類會清除舊品項。
- 設備與設備品項為獨立條件；兩者皆空、僅設備、僅品項、兩者都有，均有 SQL 測試。
- 品項選定時在同一資料庫交易建立既有 `repair_items` 記錄，僅映射客戶、品項、備註；自動編號及來源／稽核資訊由系統產生。
- 僅自動來源記錄允許未知欄位為 NULL，普通手動新增維修品仍維持原必填驗證。
- 維修品清單不再把未知狀態或數量錯當為「已收件」或 1；編輯自動記錄時不預填未知日期／數量／狀態。
- 儲存後沿用工作日誌資料範圍刷新，核對維修明細、品項及設備連結；不新增全資料載入。
- Preview 瀏覽器暫存流程同步更新，正式寫入限制不變。

## 重送與後續修改的實作保護

以下為實作採用的保護措施，不是額外新增業務狀態：

- 每次開啟表單產生送出識別碼；同內容重送取得原結果，不重建日誌／維修品。失敗交易不留下識別碼，因此可修正錯誤後重試。
- 同識別碼已成功但內容不同時，要求重新讀取已存日誌再修改，避免誤建第二筆。
- 維修品與來源事件為一對一。已登錄的來源品項在日誌中顯示唯讀，品項及其他後續資料透過既有維修品管理修改；不以日誌內容覆蓋人工補填。
- 維修品依原管理功能刪除後，後續存日誌不會重建已刪除維修品。
- 舊前端省略新欄位時保留既有來源選擇，並維持原 RPC 相容入口。
- 版本衝突、錯誤 UUID、非陣列設備、種類／品項不符、非法施工人員均拒絕。
- RLS、服務端角色檢查及 RPC 最小權限不放寬，新增外鍵均有索引。

### 驗證限制

SQL 測試使用精簡主檔 fixture，既有專案／日誌 v3 RPC 為替身；本次變更 SQL、維修品 RPC、设备履歷 RPC 為實際原始碼。瀏覽器測試使用 Preview 暫存測試資料，API 測試以受控身分與 RPC 替身隔離外部依賴。因此不宣稱已完成正式資料庫或獨立 SITE 網站端對端驗收，也不等同真實 iPhone Safari 測試。

本機未安裝 agent-browser 指令，瀏覽器技能流程改用內建 Playwright 執行。Supabase 技能影響了原子交易、RLS／最小權限、索引及隔離資料庫驗證方式。

## 如何重跑

- Node.js 24：`npm run check`。
- 資料庫驗證：在隔離測試目錄安裝固定版 `@electric-sql/pglite@0.3.14`，將 `PGLITE_MODULE` 設成該套件 `dist/index.js` 的 file URL，執行 `node scripts/verify-worklog-repair-db.mjs`。
- 瀏覽器驗證：使用 Playwright 1.62.1，必要時以 `PLAYWRIGHT_MODULE` 指向套件 `index.mjs` 的 file URL；若使用已安裝 Edge，設定 `BROWSER_CHANNEL=msedge`，執行 `node scripts/verify-worklog-repair-browser.mjs`。
- 兩支隔離驗證不讀取正式帳密、不連線正式資料庫，也不變更 NAS。
