## 2. 新增資料模型／API

### 客戶預約

沿用 work_assignments，沒有新增獨立待辦表。
- 增加 customer_id、department_id、appointment_type、appointment_date、contact_name、contact_phone、notes。
- assignment_type 增加 appointment；只有預約可無 project_id、使用 in_progress。
- 類型：repair／site_visit／quotation，介面為「客戶報修／預約場刊／索取報價」。
- 狀態：pending／in_progress／completed／cancelled。
- 客戶、科室保留外鍵，增加必要的部分索引。
- upsert_customer_appointment_v1 使用 SECURITY INVOKER、固定 search_path，僅 service_role 可執行；檢查現有管理員、指派對象、科室歸屬及 row_version。

既有 /api/inventory → Gateway：
- GET scope=appointments：回傳 customer_appointments 與已授權的客戶、科室、人員參照；一般使用者僅取得自己的預約。
- POST operation=upsert_customer_appointment：id、row_version、customer_id、department_id、appointment_type、appointment_date、contact_name、contact_phone、instructions、assignee_user_id、status、notes。
- 沿用 mutate／RPC 回應格式及成功後重讀，不以畫面先行更新冒充保存完成。
- 取消預約使用 cancelled 保留歷程，不硬刪既有工作指派。

### 整張進貨單

沿用 stock_receipts，未新增第二套库存來源或複製明細表。
- 增加 receipt_document_id UUID、receipt_line_no 正整數及部分索引。
- 同單每列維持原 stock_receipts.id；庫存仍依原進貨明細加總。
- POST operations：create_stock_receipt_document／update_stock_receipt_document。
- 傳入 document_id、原始各列 ID／row_version、日期、供應商、1～20 筆明細（品項／數量／備註）、訂貨客戶及科室。
- save_stock_receipt_document_v1 在同一交易鎖定整單及品項，檢查完整原始列集合與版本，再沿用原建立／修改 RPC。
- 同單任何一列失敗，整筆交易回滾；重複新建同一 document_id 不會重複入庫。
- 舊資料缺少可靠單號：不依日期／供應商猜測合併。保留單筆，編輯時以原穩定 ID 成為一張單。
- 表單可一次修改既有列並追加新列；既有列不會因從表單消失而被默默刪除。原刪除入口改為明確確認整張單，沿用原 delete_stock_receipts 路徑。此破壞性 SQL 流程未在本次隔離環境執行，見限制。

### 日誌附件

- site_assets 既有 work_log_id 沿用，無新附件表。
- /api/nas 的 context 與簽章綁定可選 work_log_id；無日誌的一般附件維持原路徑。
- create_contract_site_attachment_batch 帶 work_log_id 時呼叫 register_work_log_attachments_v1，驗證日誌與工作內容關聯，再沿用原 v2 登錄及回應。
- NAS 覆寫前與 SQL 登錄時均檢查不同日誌已持有的檔案路徑，避免跨日誌挪用關聯。
- NAS 与 SQL 不是跨服務原子交易；索引失敗仍會顯示失敗並保留 NAS 成果供重試。

## 3. 工作指派整合流程

建立預約 → 同一 work_assignments.id 指派使用者 → 該使用者 Dashboard 待辦顯示 → 沿用既有完成 RPC → 同一列 status=completed → 預約清單重讀後完成。

反向重開同一列後回到待辦；改派後舊負責人不再取得該筆預約。沒有以客戶名稱或文字配對，也沒有建立第二筆平行待辦。既有一般工作及取貨指派保留原流程。

一般使用者預約 scope 只補入已授權的參照資料；前端合併穩定 ID，不用部分資料覆蓋已載入的完整 CRM 快取。登出時清除 state／snapshot。

## 4. 客戶篩選資料流

沿用目前前端 snapshot 篩選架構及共用「搜尋／篩選」圖塊：
客戶分類 → 可用客戶 → 可用科室 → 實際工作內容結果集合 → 原排序與分頁。

## 5. 附件上傳優化

現有「一組」是單一檔案與一筆附件，不是 Before／After 配對。
- 日誌批次上限 30；其他附件仍為 10。
- 每檔仍最多 20 MiB；日誌整批最多 600 MiB，其他整批維持 80 MiB。HTTP 傳輸仍沿用小請求／分片，不把 600 MiB 打包成單一請求。
- 原本已是並行 2，調為有界並行 3；不是把 30 個請求全部同時送出。
- 減少重複 context 檢查；大型 File 雜湊以 WeakMap 暫存，重試不重複计算同一 File。授權、最終寫入 context、簽章及檔案完整性保護保留。
- 原本就不是 Base64；維持 File／Blob multipart 與既有 WebDAV／分片整合，不做有損壓縮或暴露 NAS 憑證。
- 逐檔保存成功／失敗狀態。27 成功、3 失敗時只重傳 3；NAS 成功但 metadata 失敗時只重試 SQL 登錄。
- 重試成果暫存限同一個開啟中的表單及相同檔案／context；未宣稱瀏覽器重整後可恢復未完成批次。
- 可證明減少重複請求與重傳；尚無真實 NAS 吞吐量提升百分比，不宣稱實體網路速度已提升多少。
