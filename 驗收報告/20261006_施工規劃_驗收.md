## 2. 資料結構

```text
projects（既有工作內容）
  └─ construction_plans.project_id
       ├─ construction_plan_assignees(construction_plan_id, user_id)
       │    └─ app_users.id（既有使用者）
       └─ site_work_logs.construction_plan_id（nullable）
            ├─ project_id（既有工作內容）
            └─ access_creator_user_id（既有不可任意改写的建立人）
```

規劃保存日期、內容、四種狀態、備註、建立人／時間／更新時間及 row_version。客戶、科室、案場、工程分類、合約與負責人沿用工作內容關聯，沒有複製主檔。啟用判斷使用 `construction`、`small_purchase`、`tender`，不依顯示名稱判斷。

有日誌（包括封存日誌）的規劃禁止刪除，可改成「取消」。空規劃採封存刪除並保留稽核。移除施工人員只撤銷後續新增權限，不刪其歷史日誌。

## 3. 權限邏輯

| 身份 | 能力與限制 |
|---|---|
| 工作內容負責人 | 以 project_workers.is_assignee 的實際 user ID 判斷；具工作內容 VIEW／UPDATE 可管理自己負責工作的規劃。具日誌 VIEW 可查看該規劃的人員紀錄，不因負責人身份自動取得修改他人日誌的權限 |
| 被指派施工人員 | 沿用工作日誌 CREATE／UPDATE／DELETE；可新增當前指派規劃的日誌，修改／封存自己建立的紀錄。一般 scoped 人員只取得該規劃入口，不增加全專案權限 |
| 管理員 | 沿用既有最高管理能力及私人資料限制；可管理規劃、維護日誌。新建規劃日誌仍須在施工指派中 |
| Viewer | 依既有 VIEW 範圍查看，不得新增／修改／刪除 |

權限由 Gateway 與 SQL 雙重驗證，不能靠改 payload 的 user ID 或 construction_plan_id 越權。原有私人客戶／私人日誌限制優先。新 RPC 不授權 anon／authenticated 直接呼叫，新增資料表啟用 RLS 並限制為後端 service_role。

## 4. 工作日誌整合

從規劃進入原工作日誌表單，自動帶入日期、工作內容、客戶／科室與施工內容，預設勾選本人。可填時段、日誌狀態、已完成／未完成等原有資訊。

保存仍走 `upsert_work_log_sections_v1`，延用原版本、冪等、稽核與其他日誌流程；新增 wrapper 只驗證規劃並在同一交易內保留關聯。一般日誌的 construction_plan_id 為 null，仍走原保存授權流程。照片／附件未另建系統，也未變更 NAS 寫入流程。

日誌保存後會重新讀取並核對內容及規劃 ID。日誌儲存不會自動完成施工規劃。負責人需自行修改規劃狀態。

## 5. Dashboard 整合

沿用首頁「工作指派」卡片。根據 construction_plan_assignees 即時產生顯示項目，使用 `construction:<plan ID>` 穩定識別；不複製寫入 work_assignments。只顯示本人未開始／施工中的安排。點擊「查看施工規劃」可進入日誌；不沿用一般任務「完成」按鈕，以免錯誤自動結束整個規劃。
