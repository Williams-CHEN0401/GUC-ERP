## 範圍與根因

截圖錯誤來自既有 SQL 儲存函式：工作日誌有來源維修品時，客戶／科室變更被拒絕。維護保養的另一層入口也要求維修品與日誌客戶／科室一致，導致先改維修品後，後续修改日誌仍失敗。共用維修事件 writer 同時鎖定來源品項，並在日誌日期變更時覆寫維修品收件日期。

維修品自己的 writer 原本就支援獨立修改，沒有反向更新日誌；因此不另建 API 或重写該 writer。

本次最小修正：

- `app.js`：解除已登錄維修品造成的種類／品項鎖定；保留原停用種類的既有選值；預覽同步解除客戶／科室／品項限制，移除維修品日期覆寫。
- Migration `20260929150841_independent_worklog_repair_edits.sql`：只替換 3 個既有函式的上述限制與日期覆寫區段，基準不符時整筆中止。保留函式 OID、參數、SECURITY DEFINER／search_path、ACL、交易、版本及重送保護。CLI 本機草稿時間戳原為 `20260929145444`，已依正式 migration 工具實際記錄更名，沒有重複套用 SQL。
- `source_maintenance_event_id` 保留作來源追溯；不刪資料、不搬移既有維修品、不回填歷史值、不新增欄位或主檔、不更動 RLS／權限。
- 每筆資料仍須選擇屬於其自身客戶的科室。已關聯真實案場設備或歷史附件的跨客戶／工作歸屬保護維持不變，避免誤移設備及附件。
- 測試讀檔器統一 SQL 換行為 Git/server 的 LF，避免 Windows autocrlf 使既有 migration 字串比對失敗；不改動歷史 migration。
