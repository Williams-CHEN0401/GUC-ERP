## 2. 權限模型

`app_users.role → app_roles → role_permissions → VIEW / CREATE / UPDATE / DELETE`。

Sidebar、路由、表單及按鈕使用相同模組權限；Gateway 重新驗證，前端隱藏不是安全邊界。admin 保留既有最高模組管理能力，但不自動取得私人資料權。既有 project_workers 工作內容授權繼續限制工作日誌。

viewer 本來已存在，未建立重複角色；可編輯既有 viewer 權限。角色代碼／名稱來自資料庫。系統角色不可刪除，仍有使用者引用的自訂角色也不可刪除。角色更新及刪除採 row_version 與資料列鎖；不自動把其他使用者轉為 admin。

客戶預約使用獨立 appointments 模組；「取消／停用」沿用既有 UPDATE 操作，保留資料，不新增硬刪除流程。

## 3. 資料可見性模型

一般讀寫需同時通過「模組／動作權限」與「資料可見性」，既有 scoped 角色再加工作內容授權。

- 管理員逐筆標記 customers.is_private，不自動推測或回填歷史客戶分類。
- 非名單成員不能讀取私人客戶及其預約、工作、日誌、附件、維修、交易等既有 FK 關聯資料；一般 admin 也不能例外。
- REST 條件在搜尋、排序、筆數限制之前加入；JSON 輸出另作防護。未完成權限計算時拒絕回應，不能靜默開放。
- 老闆新日誌保存不可修改的 access_creator_user_id；修改填報人不能解除隱私。舊日誌優先用既有最早 Audit 證據，其次 reporter_user_id，沒有稽核證據時無法完全還原歷史建立者，未擅自進行正式回填。
- 全部日誌都受限的工作也隱藏，避免從工作名稱看到日誌標題；混合公開／私人日誌的工作不批次隱藏公開日誌，但禁止外人連動改名、歸屬或寫入共用 NAS 目錄。
- 單筆查看核准是專用唯讀 API 的例外；不解除一般清單／寫入防護、不開放客戶與預約、其他日誌或附件。
- 非名單管理員不能修改／刪除名單內帳號，避免藉重設密碼冒用。
- 隱藏交易明細後，庫存由只回傳品項 ID／數量的帳冊彙總計算，不讓庫存數量跟著減少。
- 工作日誌／庫存載入不再夾帶未取得取貨／進貨查看權的明細；需要顯示庫存時只使用總量。沒有取貨查看權的日誌欄位顯示「—」，不誤報「尚未取貨」。
- ACL 更新會清除跨頁快取，較舊版本的晚到回應不會還原私人資料。

## 5. 工作日誌審核流程
