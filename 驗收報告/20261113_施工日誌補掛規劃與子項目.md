# 施工日誌補掛／改掛施工規劃與子項目

查核日期：2026-11-13（Asia/Taipei）。來源為 GitHub Williams-CHEN0401/GUC-ERP，已 fetch 並確認 main 2ab609ed079e582dd37f34dc3995d3d776d5b519。本機分支：codex/construction-log-relink-1113。

## 原因與範圍

2026-10-16 的規劃關聯功能原本允許已授權人員，將既有日誌補掛或改掛至同一工作內容的施工規劃。2026-11-04 導入施工權限的 migration 重新定義 assert_construction_log_access_v1 時，恢復了「日誌必須已屬於目標規劃」的嚴格比對，覆蓋原有補掛路徑。此檢查發生在角色／他人日誌操作判斷前，因此管理員也會收到「日誌與施工規劃不相符。」。

正式資料唯讀查核：

- 土庫國小，工作編號 2610012：11/10、11/12 的日誌尚未關聯規劃，補掛「配管作業」及其子項目被拒絕。
- 鳳山高中「強化校園安全設備採購」，工作編號 2611023：兩筆日誌原掛「綜合大樓監視器配管拉線」，改掛同案的另一施工規劃時被拒絕；原規劃內換子項目原本可成功。

## 修正

只新增 20261113054605_construction_log_relink_existing.sql，替換一個既有授權函式，保留原 OID、擁有者、ACL、security invoker 與 search_path。不建立新表、欄位、Auth、客戶或權限模型，不回填或自動改掛真實日誌，不更動前端版面。

補掛／改掛必須同時符合：

1. 原日誌與目標規劃屬於同一工作內容。
2. 具有既有施工規劃／日誌查看及修改權限；目標規劃有效、未取消，且使用者是指派人員或具有既有管理權限。
3. 未掛規劃的日誌沿用 assert_regular_work_log_access_v1；已掛規劃的日誌沿用 construction_log_action_v1，不因被指派規劃就獲得修改他人日誌的權限。
4. 原有私有客戶、子項目歸屬、資料版本、送出識別碼、觸發器及原子交易檢查仍然生效。

## 同案並行修改的鎖定順序修正

正式驗證時發現改掛規劃與來源規劃日誌同時被操作，可能發生鎖定順序相反的 deadlock。新增 20261113101716_construction_log_relink_lock_order.sql，同樣只替換既有 assert_construction_log_access_v1：在鎖定共用工作內容前，依 UUID 固定順序取得來源與目標規劃的列鎖；等候期間若日誌關聯已被其他人變更，回傳重新載入提示，保留既有版本衝突保護。

scripts/verify-construction-relink-concurrency.mjs 僅接受指定隔離 Docker 資料庫設定，以兩個原生 PostgreSQL 工作階段重現舊 deadlock，並驗證新鎖定順序讓兩邊完成、原資料全部回滾。既有 545 項測試、9 組最新授權規則 Gateway／SQL 流程均再次通過。
