## 2. 單據與明細結構

- Header 等效結構：`stock_transaction_documents`，主鍵 `(kind,id)`；kind 為 receipt／pickup。保存 UUID、不可變的編號範圍 ID、實際日期快照、流水、顯示單號及來源 request ID。
- 進貨 Detail：原 `stock_receipts`，以 `receipt_document_id` 找登錄表的 receipt ID；原明細 `id`、`receipt_line_no`、訂貨客戶／科室連結保留。新增 `receipt_document_no`。
- 取貨 Detail：原 `pickup_records`，新增 `pickup_document_id`／`pickup_document_no`。原明細 `id`、request_id／request_row、工作日誌／指派／帳號連結保留。
- 不新增第二套庫存帳本。觸發器在既有入口寫入時指定單據關係，修改時保留號碼與單據 ID。新增的整單 RPC 驗證「整張明細 ID 集合＋各筆 row_version」。
- 已刪單的編號登錄保留，避免重發相同編號；這與工作內容名稱可在刪除後重用是不同規則。

## 3. 進貨單號

編號範圍 = 實際進貨日期＋廠商 **ID**，不是名稱或資料建立時間。

同廠商同日：`20261002`、`20261002-2`、`20261002-3`。不同廠商／隔日各自從無尾碼開始。修改原單（包含日期、廠商、品項、數量）保留原單號及編號快照，不重編。

## 4. 取貨單號與並行保護

編號範圍 = 實際取貨日期＋工作內容 **ID**。工作 B 在 2026-10-03 實際驗證為 `20261003`、`20261003-2`；不使用今天或 created_at。原單修改不重編。

編號在同一 SQL 交易內，以 kind＋scope ID＋日期取得 advisory transaction lock，再取流水；另有唯一約束保底。request 鎖防止重送、單據鎖與 row_version 防止整單互相覆蓋。舊混合工作批次依固定 scope/date 順序取得編號鎖，仍保留輸入順序與 request_row。

PostgreSQL 18.4（Windows、只監聽 127.0.0.1）的 12 個真正獨立連線已實測進貨／取貨各 12 張三明細並行；各 36 明細、流水無重複。另測沒有共同庫存鎖的編號競爭、反向多工作批次、相同 request 重送、同單同版本競爭，以及觀察 pg_stat_activity 真正鎖等待後 ROLLBACK 釋放。共 8 項通過。测试服務執行完已停止。

## 5. 清單與編輯

原取貨直接遍歷明細，故一個品項一列；原進貨雖已有 document_id 聚合，沒有批次 ID 的舊列仍各是一單。

現在先依單據 ID 分組，再搜尋、篩選、排序及分頁。品項種類數是 distinct inventory_item_id；總數量是全部明細 quantity 加總。清單最多顯示前兩個品項摘要，剩餘顯示「另有 N 筆明細」；搜尋仍涵蓋所有明細。

雙擊開啟整單，修改原列使用原 ID，可新增或移除列，最後一次原子保存。移除需要既有 DELETE 權限；新增需要 CREATE；僅 UPDATE 的帳號仍只能改原列。沒有新增角色或放寬匿名／一般登入角色資料表權限。

實際 Chrome UI 已走過：新增三明細→保存→重整→整單編輯→改日期／數量／增刪列→保存→重整；進货由 6 改為 15、取貨由 6 改為 9，單號不變。最終 migration 版另重測整單編輯保存，取貨 20261002-12 合計 9、進貨同號合計 10。13 張進貨、14 張取貨的每頁 10 筆分頁正確，排序尾碼 2 在 10 之前。兩邊關鍵字＋日期＋範圍篩選正常。

Chrome 390×844 窄螢幕檢查：表格在自身容器水平捲動，頁面 scrollWidth=clientWidth=375；表單沒有水平溢出，儲存按鈕可見。這是 Chrome viewport 測試，不是 iPhone Safari 實機驗證。瀏覽器最後抽查 error/warn 為空。

## 6. 舊資料與正式更新前提

需要新增本次 migration，然後更新 inventory-gateway，再發布 ERP 前端。**三層均尚未正式更新。**

- 舊進貨只有確定的 `receipt_document_id` 才合併；缺少時用原明細 ID 維持單筆。不會因同日同廠商就猜測是一張單。因此截圖中若三列沒有原批次識別，這三列不會擅自合併。
- 舊取貨依 `request_id`＋實際 project_id／pickup_date 分組；不同脈絡的舊混合批次分開。沒有 request_id 的舊列保留獨立。
- 既有進貨同 document_id 如果日期／廠商互相衝突，migration 直接停止並回復，須先人工確認。
- 有範圍 ID 的舊單按原 created_at、id 決定流水分配順序；顯示單號日期取實際交易日期。缺廠商 ID 的舊進貨保留「舊單（未編號）」，不假造廠商。
- 回填不改原業務欄位、數量及來源連結；既有更新觸發器可能刷新 row_version／updated_at／稽核資料。正式更新需短暫停止編輯並要求舊表單重載。
- 本次正式 SQL 編輯器未能載入，**未取得正式歷史筆數、孤立列清單、即時刪除函式定義／ACL**。已提供唯讀 preflight，不能把隔離合成資料結果當作正式資料盤點。
- 隔離 fixture 的刪除入口是原契約的精簡實作；其餘相關保存／同步 RPC 讀取實際 migration。正式發佈前仍须比對真實刪除函式／trigger、盤點 legacy 分組、備份及前後業務欄位指紋。沒有做正式試寫。
- 保留舊 API 簽章及既有單筆入口；正式更新先 DB、再 Gateway、最後前端。舊版單筆修改 API 不會自動改成整单修改；當次新增的 UI 都使用整單保存路徑。若回復前端版本，保留已新增單據 metadata 與業務資料，不以 DROP TABLE 回滾。
